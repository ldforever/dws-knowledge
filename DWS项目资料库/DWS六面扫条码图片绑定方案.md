# 物流六面扫 DWS 软件：条码与图片绑定方案

## 1. 项目背景

- 目标：用 Node.js 开发物流六面扫 DWS（体积测量 / 称重 / 读码）软件，替代大华 DWS 方案。
- 动因：迁移到 ARM 架构，降低工控机成本。
- 相机方案：18 台智能相机，相机端直接完成条码解析并输出条码。
- 传输方式：
  - 条码结果：通过 TCP 实时传输到本地电脑；
  - 拍摄图片：通过 FTP 传输到本地电脑。
- 核心诉求：实现"一个包裹 = 一个条码输出 + 18 张照片"的准确绑定。

---

## 2. 核心设计思想

**条码和图片不是一对一去"配对"，而是两条各自独立的事件流，先分别聚合成"包裹实例"，再在包裹层面绑定。**

原因：

- 18 台相机并非同一时刻触发，同一包裹的事件在时间上是一个窗口，而不是一个点；
- 图片走 FTP 传输，到达电脑的时间通常滞后几百毫秒到几秒，不能按到达顺序配对；
- 存在漏读、一包多码、包裹间距过近等现场情况，直接匹配必然出错。

因此引入**包裹窗口（Parcel Window）**概念：所有事件（条码、图片、触发信号）先归属到同一个包裹实例，再进行融合与输出。

---

## 3. 三条数据流

| 数据 | 来源 | 传输 | 实时性 | 关键信息 |
| --- | --- | --- | --- | --- |
| 条码事件 | 智能相机解析 | TCP | 毫秒级 | 相机号、条码、读取时间 |
| 图片文件 | 相机拍摄 | FTP | 秒级延迟 | 相机号、**拍摄时间（文件名）** |
| 物理触发信号（可选） | 光电开关 / 编码器 | IO / 串口 / PLC | 实时 | 包裹开始 / 结束 |

> ⚠️ FTP 文件的 mtime（修改时间）不可靠，必须以**图片文件名内嵌的拍摄时间戳**为准，或者现场统一校时后以可信时钟为准。

---

## 4. 先定义"一个包裹"

包裹边界是所有聚合的前提。三种方案的优先级如下：

### 4.1 光电开关（推荐）

隧道口布置光电开关，ON → OFF 即视为一个包裹：

- 每个包裹自动获得递增序号 `parcelId`；
- 分割准确，不依赖读码结果；
- 成本低、可靠性高。

### 4.2 光电 + 编码器（最优）

在光电基础上增加编码器：

- 可获得包裹长度和精确位置；
- 能为每台相机计算精确的时间窗（按包裹在传送带上的位置推算各相机的曝光时刻）；
- 适合对绑定精度要求高的场景。

### 4.3 读码静默期切包（兜底）

无任何传感器时的兜底方案：

- 所有相机累计 N 毫秒（如 500ms）无新条码事件，则关闭当前包裹；
- 缺点：漏读包裹、两个包裹贴太近时会产生错误切分。

> 建议：现场流水线连续过包时，至少保留一个光电信号，否则软件中的"归属判断"永远是模糊问题。

---

## 5. 软件汇聚模型

软件维护一个"打开中的包裹窗口"，核心数据结构如下：

```js
Parcel {
  id: 10086,
  startTs, endTs,          // 由光电或读码静默期决定
  codes:  [{ camera, code, readTs, quality }],
  photos: [{ camera, filePath, captureTs }],
  fusedCode: "9400...",    // 最终输出
  status: opening -> closed -> output
}
```

### 归属规则

1. **条码事件**（TCP 到达）：
   - 若当前无打开的包裹，则新建一个；
   - 事件时间落在窗口内 → 归属当前包裹。

2. **图片文件**（FTP 到达）：
   - 不按到达顺序归属；
   - 解析文件名中的拍摄时间戳；
   - 满足 `拍摄时间 ∈ [包裹开始 - 50ms, 包裹结束 + 50ms]` 且相机号匹配 → 归入对应包裹。

3. **窗口关闭**：
   - 触发条件：光电落下 + 宽限期结束；
   - 或：读码静默期达到阈值（兜底模式）。

4. **关闭后处理**：融合条码 → 移动图片 → 持久化 → 输出记录。

### 状态机

```
           光电 ON / 首个事件
  ┌──────────────────────────────┐
  │            opening           │
  │  持续接收 codes / photos     │
  └──────────────┬───────────────┘
                 │ 光电 OFF + 宽限期 / 静默期超时
                 ▼
             ┌────────┐    有码     ┌────────┐
             │ closed ├───────────→│ output │
             └────────┘            └────────┘
                 │ 无码
                 ▼
            人工复核队列（保留 18 张图）
```

## 6. 条码融合规则

18 台相机可能同时读到同一个码，也可能一包多码。融合优先级如下：

### 6.1 去重（最常见）

同一包裹窗口内，**完全相同**的条码直接去重。

> 实际场景中约 80% 的情况属于"六面多相机互补读到同一个码"。

### 6.2 冲突裁决

同一窗口出现不同条码时，按以下顺序裁决：

1. 相机优先级（如顶部大相机 > 侧面相机，可配置）；
2. 读取质量（协议支持 quality 字段时）；
3. 校验位 / 码制规则校验。

### 6.3 一包多码

合包件（一箱多件 / 一包多码）时，输出需支持主码 + 子码结构。

> ⚠️ 需与业务方确认实际规则。

---

## 7. 图片绑定要点

### 7.1 最优先争取的能力：相机自述绑定

智能相机的工作链路是"拍到图 → 解码 → 出码"，相机天然知道某次解码对应哪一帧图。

**建议向相机厂家争取：条码 TCP 报文中附带图片文件名或帧号。**

- 若能实现，绑定从"18 台相机时间对拍"降级为直接映射，可靠性完全不同；
- 这是协议层面成本最低、收益最大的一个字段。

### 7.2 若协议只输出条码，则必须做好三件事

1. **统一时钟**：现场所有相机 + 电脑统一走 NTP，时间偏差压到几十毫秒内；
2. **延迟标定**：每台相机单独标定固定延迟偏移（触发→成像、成像→FTP 落盘），存入配置表；
3. **图片命名规范**：文件名必须包含相机号与拍摄时间，例如：

```text
TOP1_20260903103015123.jpg
```

### 7.3 图片目录规划

```text
ftp/raw/                    # FTP 接收临时目录
  TOP1_xxx.jpg
  ...
parcels/
  10086/
    TOP1_xxx.jpg            # 18 张按面/相机归档
    ...
```

建议同时维护相机号 → 面位（6 面 × 3 相机）的映射表，输出时附带 `face` 与 `camera` 信息。

---

## 8. 漏读处理（必须提前设计）

现场存在标签缠绕、褶皱、反光等情况，导致整包无码。处理原则：

- 包裹窗口**照常关闭**，18 张图照常归档；
- 输出一条 `code = null` 的记录；
- 图片进入**人工复核队列**；
- 界面 / 下游系统可按包裹号调出该包裹全部图片人工补码。

> ⚠️ 若未预留该通道，现场一天漏几百件后所有后续数据都会错位。

---

## 9. 软件模块划分（Node.js / ARM）

单 Node 进程即可承载全部逻辑，ARM 平台负载很低：

| 模块 | 职责 | 关键点 |
| --- | --- | --- |
| `tcp-server` | 接收各相机条码事件 | 每相机独立端口或按相机号路由 |
| `ftp-server` | 接收相机推送图片 | 如 Node 包 `ftp-srv`，落盘 raw 目录 |
| `aggregator` | 包裹窗口维护、事件归属 | 状态机核心 |
| `fusion` | 去重 / 融合 / 冲突裁决 | 可配置优先级表 |
| `archiver` | 包裹关闭后归档图片、写记录 | raw → parcels/<id>/ |
| `output` | 推送结果给下游 | WMS / 分拣 / 本地屏 |

### 持久化建议

- 本地使用 SQLite 即可；
- 保留**全量原始事件日志**，便于现场追溯、回放、重新绑定；
- 建议事件流具备可重放能力（如 TCP 事件落盘后再进入聚合器）。

### 性能说明

- ARM 上瓶颈不在 CPU，而在图片 IO；
- 条码 TCP 事件量极小；
- Node 单进程完全可承载，无需引入复杂中间件。

## 10. 待确认问题（影响后续细化）

1. 隧道口现有光电 / 编码器信号吗？还是只能依赖相机自触发？
2. 相机条码 TCP 报文目前包含哪些字段？能否增加时间戳或图片文件名？
3. 一个包裹固定一个码，还是可能多码（合包 / 一箱多件）？
4. 出码对象是谁——上位机系统、分拣机、还是本地大屏？决定输出协议。

---

## 11. 总结

绑定方案的核心不是"匹配算法"，而是**工程上的时序纪律**：

1. 用物理信号或静默期先切分"包裹"；
2. 条码、图片各自携带可信时间戳，归属到包裹窗口；
3. 窗口关闭后做融合、归档、输出；
4. 争取相机报文携带图片文件名/帧号，将时序绑定问题直接消除；
5. 漏读通道提前设计，保证整条数据链不中断。
